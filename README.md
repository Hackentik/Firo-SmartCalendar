# 🍊 Firo SmartCalendar

**Веб-приложение для бронирования кабинетов и напоминаний в офисе**

Календарь с недельным и месячным видом, бронирования и отдельные напоминания,
модерация регистрации администратором, внутренние уведомления с упоминаниями коллег.

**Репозиторий:** https://github.com/Hackentik/Firo-SmartCalendar

## Возможности

- 📅 **Месячный и недельный календарь** с навигацией вперёд/назад, подсветкой
  сегодняшнего дня и кликом по ячейке для быстрого создания брони
- 🔔 **Напоминания** — отдельная от бронирования сущность: можно создать напоминание
  без кабинета (просто "не забыть про X") или привязать к конкретному кабинету, без
  проверки занятости — это не бронь, а просто пометка на календаре
- 📣 **Упоминания коллег с уведомлениями** — при создании напоминания можно указать
  участников, им придёт внутреннее уведомление (колокольчик в навигации со счётчиком
  непрочитанных, обновляется автоматически раз в 30 секунд без перезагрузки страницы)
- ✅ **Модерация регистрации администратором** — новый сотрудник может войти
  в систему только после того, как администратор одобрит его заявку
- 🏢 **Публичный каталог кабинетов** — вместимость, оборудование и бронирование
  в один клик, доступно всем сотрудникам, не только админам
- ⏱ **Проверка занятости в реальном времени** (AJAX) при выборе времени и кабинета
- 👥 **Управление участниками** встречи с предупреждением о превышении вместимости
- 🎨 **Цветовая маркировка кабинетов** — брони на календаре подсвечиваются цветом своего кабинета
- ♾️ **Кабинеты без ограничения вместимости** — для актовых залов и подобных пространств
- 📤 **Экспорт брони в `.ics`** — добавление встречи в Outlook / Google Calendar / Apple Calendar
- 🔍 **API поиска свободных кабинетов** по времени и минимальной вместимости
- 🔐 **Роли администратора и сотрудника**
- 🔄 **Автообновление на сервере** — сервер сам подтягивает новые коммиты из GitHub
  и перезапускается, без ручного захода по SSH (см. [деплой](#деплой-на-сервер-и-автообновление))
- 🛡️ CSRF-защита форм, хеширование паролей, секретный ключ через переменные окружения

## Быстрый старт

```bash
# 1. Клонируем репозиторий
git clone https://github.com/Hackentik/Firo-SmartCalendar.git
cd Firo-SmartCalendar

# 2. Создаём виртуальное окружение
python3 -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate

# 3. Устанавливаем зависимости
pip install -r requirements.txt

# 4. (опционально) задаём секретный ключ для разработки
export FIRO_SECRET_KEY="какой-нибудь-случайный-ключ"

# 5. Запускаем
python app.py
```

Приложение поднимется на `http://127.0.0.1:5000` (или `http://IP_СЕРВЕРА:5000` на VPS —
сервер слушает `0.0.0.0`, так что порт должен быть открыт в файрволе). База
`firo_calendar.db` создастся автоматически при первом запуске.

> Первый зарегистрированный пользователь **автоматически становится администратором**
> и входит сразу. Все последующие регистрации попадают в очередь на модерацию —
> зайдите в **Управление → Пользователи**, чтобы одобрить или отклонить заявку.

### Переменные окружения

| Переменная            | По умолчанию                     | Назначение                          |
|------------------------|-----------------------------------|--------------------------------------|
| `FIRO_SECRET_KEY`      | `dev-only-change-me-in-production` | Секретный ключ Flask — **обязательно** задать своё значение в продакшене |
| `FIRO_DATABASE_URI`    | `sqlite:///firo_calendar.db`      | Строка подключения к БД (можно указать PostgreSQL/MySQL) |
| `FIRO_DEBUG`           | `false`                           | Режим отладки Flask — держите `false` на публичном сервере |
| `FIRO_PORT`            | `5000`                            | Порт, на котором слушает приложение |

## Деплой на сервер и автообновление

Подробная пошаговая инструкция — в [`deploy/README.md`](deploy/README.md). Коротко:

1. Клонируете репозиторий на сервер, ставите зависимости в venv
2. Регистрируете `deploy/firo-smartcalendar.service` как systemd-сервис —
   приложение само поднимается после падения или перезагрузки сервера
3. Добавляете `deploy/autoupdate.sh` в cron от имени root — раз в 5 минут сервер
   сам сравнивает себя с GitHub, подтягивает новые коммиты и перезапускается

После этого обновление сервера — это просто `git push` в свой репозиторий,
без захода по SSH.

| GET/POST | `/login`                              | Вход (заблокирован для неодобренных)   | все          |
| GET   | `/calendar?view=month\|week`             | Календарь (брони + напоминания)        | одобрен      |

| POST  | `/booking/<id>/delete`                   | Удаление брони                         | автор / админ |
| GET   | `/booking/<id>/export.ics`               | Экспорт брони в `.ics`                 | автор / админ |
| GET   | `/reminders`                             | Список напоминаний                     | одобрен      |

| GET   | `/notifications`                         | Все уведомления пользователя           | одобрен      |
| POST  | `/notifications/<id>/read`               | Отметить уведомление прочитанным       | владелец     |

## Роли и права

- **Администратор** — одобряет или отклоняет заявки на регистрацию, управляет
  кабинетами, назначает других администраторов, редактирует и удаляет любые
  бронирования и напоминания.
- **Сотрудник** — после одобрения администратором может создавать бронирования
  и напоминания, редактировать и удалять только свои, видеть каталог кабинетов
  и общий календарь.
- **Заявка на рассмотрении / отклонённый пользователь** — не может войти в
  систему до решения администратора (даже зная правильный пароль).

## Известные ограничения

- Проверка занятости кабинета (`SELECT`, затем `INSERT`) не обёрнута в блокировку
  на уровне БД — при одновременном бронировании одного и того же слота двумя
  пользователями в одну миллисекунду теоретически возможна гонка. Для
  продакшена с высокой нагрузкой стоит добавить транзакцию с блокировкой строк
  (`SELECT ... FOR UPDATE` в PostgreSQL) или уникальный индекс на уровне БД.
- Колокольчик уведомлений обновляется через опрос (polling) раз в 30 секунд,
  а не мгновенно — для мгновенной доставки нужен WebSocket (Flask-SocketIO),
  что усложняет деплой (нужен eventlet/gevent).
- Автообновление сервера (`deploy/autoupdate.sh`) проверяет GitHub раз в 5 минут
  через cron, а не мгновенно по пушу — для мгновенного деплоя нужен вебхук.
- Если обновляете базу с более ранней версии проекта — новые таблицы
  (`reminders`, `notifications`) создадутся автоматически при следующем запуске
  без потери существующих данных. Но если у вас совсем старая версия без
  `approval_status` у пользователей или с обязательным `capacity` у кабинетов —
  удалите старый `firo_calendar.db` перед первым запуском (или сделайте миграцию).
